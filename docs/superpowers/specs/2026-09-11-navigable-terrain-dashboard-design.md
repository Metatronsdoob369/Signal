# Navigable terrain dashboard: decision log

Date: 2026-09-11. This is a record of decisions, not a proposal. Joe's brief: needle-moving metrics on a dynamic dashboard, the actual metrics chosen with each client, Cosine+ in the room, starting with local Birmingham clients; the dashboard is the human version of what an agent experiences in the spectral engine, navigation not retrieval; heat good, cold bad, across everything; "do what makes sense, make a decision."

## Decisions

1. **Reader is the client.** Non-technical site owner. Fix detail is one click down. The operator (Cosine+) composes the dashboard with the client during onboarding; the composition is per-site config, like the experiments switch.
2. **Metrics are a catalog, composed per site.** A metric qualifies if the embed or the server can observe it deterministically, it has a time series, it maps to a fix or a decision, and its label says exactly what was measured. Catalog v1: visits; visits from search; visits from AI answer engines (referrer table maintained like the bots table); direct and social; contact actions (mailto, tel, form submit, elements marked `data-signal-goal`) and contact rate per 100 visits; real-visitor p75 LCP, INP, CLS against Core Web Vitals thresholds; SEO score; AIO score; open fixes. Default four tiles for a new site: Visits, Contact actions, Speed, AIO. Each tile: this period against the previous, sparkline, sample size, window. A delta renders only when both periods have data. Zero reads as zero. No lift language. The AI tile states that Signal counts visits arriving from AI engines and cannot see mentions inside answers.
3. **Dynamic means trends first, live second.** Weekly deltas with sparklines from daily rollups. A polled endpoint for "last visit, visits in the last hour" gives the live pulse; streaming only if a client's traffic ever makes it matter.
4. **Data path is telemetry plus rollups (Approach A).** Pack v0.3 sends a small `visit` event on every load: path, referrer host reduced client-side to a hostname and classified server-side into a source class, device class, real-user vitals, engagement, and contact actions on unload. Visits roll up per page per day. The structural audit runs only when a page's structure fingerprint changes, or at most once per page per day, so audits and findings stop growing per visit. Deriving trends from per-visit audits (B) and third-party analytics (C) were considered and rejected: B grows the wrong tables and aggregates JSON; C breaks the one-embed thesis and adds an account per client.
5. **The primary surface is the site's terrain.** Pages are points. The client navigates it the way an agent navigates spectral terrain. The terrain contract takes the engine's shape (heat, shatter, kind, zone, recommendation, nearest canonical, repair) so an engine-produced terrain pack could replace the native one later without touching the dashboard. The terrain is Signal-native and deterministic: no Qdrant, no Ollama, no page content leaving the browser. Running pages through the engine itself was considered and deferred: it needs Qdrant, a server-side crawl, and a canonical-pages calibration.
6. **The law: temperature is health. Hot good, cold bad, everywhere.** Heat = overall score / 100 from the rule engine, an absolute weighted share of applicable rules passed, so it is meaningful for a one-page site. Shatter = 1 − heat. Zones use the thresholds the dashboard already colors by: hot at 80 and above (ANCHOR), warm at 60 to 79 (REVIEW), cold below 60 (SHATTER_RESOLVE). Signal's own code husk already classifies hot/warm/cold this way. Tiles, deltas, badges, the transect, and the terrain obey the law: warming is improving, cooling is regressing. Copper family for warm, frost and ash for cold. Sage stays line-work only. No green and red traffic lights. No cyan.
7. **Elevation is substance, not attention.** Substance = evidence density the page gives models to work with: words, structured-data nodes, definition sentences, lists and tables, answer words, a summary block. Weighted v0 priors, stated as priors. Reason: attention needs telemetry that does not exist yet, so an attention terrain would be flat on day one; substance is deterministic, nonzero on day one, honest, and it grows as a client publishes richer pages. Attention becomes luminance and pulse on each point once visits exist. The walk then goes from the client's hottest ground toward the coldest, most-visited points; attention weight = attention × coldness, ranked. That ranking is the needle in the engine's terms: cold points warming over time.
8. **A one-page site is one hill.** Height from substance, color from health, the UI says so. Signal never synthesizes a landscape a site does not have. Multi-page layout in phase 0 is a deterministic golden-angle spiral ordered by path; fingerprint-based neighborhoods (k-NN heat from the husk builder, internal links as edges) come in phase 2.
9. **Repair vector = the next fixes.** Top failing rules by severity then weight, named on the point's panel. Projected score if they ship is deterministic re-scoring and lands in phase 2.
10. **Silence rules stand.** A dimension without evidence reads unknown, never 50. A tile without data does not render. No cross-tenant benchmarks, ever.
11. **Visual constitution.** visionOS glass grammar: translucent panels that take their tint from what is behind them, backdrop blur with vibrancy, a thin specular rim, layered depth that responds to the pointer, rounded panels, restrained motion. Held to Joe's `cosine-threejs` philosophy: Kevlar Ferrari matte, Porsche restraint, one accent, Apple Pro dark, no neon, content is the hero. Legibility on glass is a hard requirement: body text at AA contrast against the blurred backdrop, measured, not assumed. Reduced motion and no-WebGL fall back to a 2D contour rendering (marching squares, the lander's TopoField algorithm ported into Signal).
12. **Rendering.** Three.js in a client component, dynamic import without SSR, one slow auto-rotating camera, a heightfield ground with vertex colors, points as emissive markers, glass HUD tiles as DOM over the canvas. Three.js lives in Signal only, never in the lander.
13. **Ships dark.** The terrain route lives under the token dashboard at `/dashboard/[token]/terrain`, gated by `TERRAIN_DASHBOARD=1`. Unset means 404. It is not a throwaway: the terrain math is unit-tested; the render is verified by screenshot.

## Phases

- **Phase 0 (this branch):** terrain math module with tests; contour fallback with tests; flagged route; Three.js scene; glass HUD from existing scores; screenshot on the lander's real audit.
- **Phase 1:** pack v0.3 visit events, visits table, daily rollups, metric catalog as pure functions, HUD tiles with deltas and sparklines, attention as luminance.
- **Phase 2:** page panel (position, band, trajectory, repair vector with projected score), the walk, fingerprint neighborhoods.
- **Phase 3:** live pulse endpoint, strip composition UI for the operator, audit dedup by structure fingerprint.
- **Phase 4 (optional, per client):** Google Search Console connection for impressions, clicks, queries.

## Residuals

- Signal has no public origin; nothing here reaches the live lander until that deploy.
- Substance and rule weights are priors. Revisit after real client pages have run.
- The referrer table for AI answer engines needs a dated `AS_OF` and quarterly review, like the bots table.
- Glass performance on the Intel iMac is measured in phase 0 and recorded here.
